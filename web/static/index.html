      Add --response to compare the output, --job-spec and --request to compare the input, or --json for a machine-readable report.

      KNOW THE SCOPE

      Integrity, with clear limits.

      The receipt commits to the task specification and response bytes. Model and usage fields inside those bytes are indirectly bound when the supplied content matches.

      Transformed API responses may differ from the upstream bytes the TEE signed. Historical evidence with expired certificates is refused. Request-ID lookup uses the public buyer evidence API; only your own requests are accessible.

      COMMON QUESTIONS

      Frequently asked questions

      What does the verifier actually verify?

      It checks the receipt's canonical encoding and signature, hardware attestation, and the application identity you expect. Together, these checks establish that the receipt was signed by a key bound to a supported trusted execution environment (TEE) running the expected application.

      The receipt records the upstream host and path, execution times, HTTP status, completion state, and content hashes. Request and response content comparisons are reported separately.

      Where do I download an execution receipt?

      Sign in to the Hive Console, open Call Records, and select your call. In the call details, choose Download for verifier for an execution attempt with an archived receipt. The download is named receipt-<execution-id>.cbor.

      A call may contain several attempts. Download and verify each receipt separately. Attempts without an archived receipt have no receipt to download.

      Which files do I need to start verification?

      Start with the original CBOR receipt and an independently trusted application identity. Production receipts include their hardware evidence, so they normally need no additional evidence file.

      Raw request and response files are optional inputs for content comparisons. Comparing a request also requires its task specification.

      What is the trusted application identity, and where do I get it?

      It is the full snp-app: identity followed by the 64-character lowercase hexadecimal hash of the TEE application you expect to have run. Obtain it from a TEE release source you independently trust.

      Use the linked release guide to check the published catalog and signing key through an independently trusted channel. This page does not automatically verify catalog signatures or trust the identity declared inside a receipt. Without an independently trusted identity, application trust cannot be verified.

      What is hardware evidence, and when do I need to provide it?

      Hardware evidence contains the attestation report and related certificate material used to check the TEE's hardware identity and its binding to the receipt's signing key and application. The verifier checks supported AWS SEV-SNP evidence against its embedded AMD and AWS trust roots.

      Production receipts already include this material. If a receipt contains only an evidence hash, verification reveals a Hardware evidence input. Supply the file that matches the signed hash, then verify again. An arbitrary evidence file cannot establish trust.

      What is a task specification, and why is it missing from my download?

      The task specification, or JobSpec, describes the job Hive sent to the TEE. It includes a hash of the upstream request body, and its own hash is signed into the receipt. Providing both the original specification and request body lets the verifier check that binding.

      Hive currently archives receipts and task hashes, without the complete task specifications. Call Records therefore provides the receipt only. A specification cannot be reconstructed from its hash or billing metadata. Leave this input empty when checking receipt authenticity.

      How do execution IDs differ from request IDs, and where can I find them?

      A request ID identifies a buyer call. An execution ID identifies one attempt to serve that call; retries can give one request several execution IDs.

      Find an execution ID under its attempt in Call Records, in the receipt filename, or under Signed execution details → job id in the verification report. It is 32 lowercase hexadecimal characters. The TEE signs this execution ID; the request-to-execution mapping is supplied by Hive.

      How do Receipt file and Request ID modes differ?

      Receipt file verifies a file you already downloaded. It works on this static website and runs locally in your browser after the engine loads.

      Request ID downloads your receipts using your buyer API key and then verifies the selected attempt locally. The web lookup currently requires the local bridge started with tokhive-verify serve; it is unavailable on the static website alone. For another Hive environment, configure the bridge with --api-base-url. Use your buyer API key to access your own requests.

      What do Verified, Incomplete, and Failed mean?
      • Verified: the required trust checks and comparisons for supplied content passed.
      • Incomplete: no check failed, but a required application expectation, hardware evidence file, or task specification is missing.
      • Failed: at least one check failed. Read that check's explanation before trying again.

      Hardware certificates are checked at the current time. Expired historical evidence can fail even when the receipt's signature remains valid.

      Why can a receipt be verified while its request and response remain unverified?

      Receipt authenticity and content comparison are separate checks. A verified receipt establishes trust in its signed execution fields and hashes. Comparing those hashes requires the corresponding original content files.

      If you provide no request or response, those contents remain unverified. Check the separate Request and Response results before concluding that your content was compared.

      How do I compare content, and why might a saved body fail to match?

      Expand Compare request or response content (optional). Supply the exact upstream response body to compare output, or the complete canonical-CBOR task specification and exact upstream request body to compare input.

      The bytes must match what the TEE processed. Formatting JSON, copying rendered text, protocol translation, compression or decompression, and request adaptation can change those bytes. A client-visible body may therefore differ from the signed upstream content. Files from another execution can also fail to match.

      Does verification prove the model, token usage, or bill is correct?

      Matching request and response content can bind model names and token counts declared in that content to the receipt. The verifier does not independently identify the model the upstream actually ran or recount tokens.

      The receipt has no independent model, token usage, or pricing fields. Prices, commissions, and wallet charges belong to Hive's accounting records and are outside this verifier's checks.

      Why can a failed or truncated execution have an authentic receipt?

      A TEE can sign an accurate record of an unsuccessful execution. Receipt authenticity checks who signed the record and whether its contents are intact.

      Inspect the signed HTTP status and completion state to see whether the execution completed successfully, failed, or was truncated. A verified receipt alone does not establish successful delivery of a complete answer.

      Are my files or API key uploaded, stored, or included in reports?

      Selected receipt, evidence, task specification, request, and response files stay in your browser. Verification runs in a local Web Worker using WebAssembly, and these files are not uploaded to the verifier server.

      In Request ID mode, your buyer API key is sent to the local bridge and then to the configured Hive API to retrieve your receipts. The verifier does not persist it, put it in URLs, or include it in reports, and clears the key input after a successful download.

      Exported reports include verification results and signed execution metadata. They do not include your API key or copies of your local request and response files.
